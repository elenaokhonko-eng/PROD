## Decisions made under the defaults

| # | Decision | Why |
|---|---|---|
| D1 | One server switch, `PAID_STAGES_ENABLED`, gates both paid products. Anything other than exactly `true` (including unset) means off: checkout returns 409 `product_not_available` with `availableFrom`, and the capabilities response turns both buy buttons off. | A missing setting can never take payments. One switch is simpler than one per product for a launch where both are off. The design's bank-pack emergency switch (`BANK_PACK_ENABLED`) stays a stage 2 item. |
| D2 | The "available from" date comes from `PAID_STAGES_AVAILABLE_FROM` (ISO date), defaulting to 2026-12-01, the stage 2 date in the costed plan. | Changing the date is a settings change, not a code change. |
| D3 | The SRF section of the free evaluation is written by the server from `rules/srf.ts`; the model's prompt and output schema no longer contain SRF signals, and any model sentence mentioning the SRF, IMDA or a telco fails the output check. | Elena: "server-only SRF verdict". Simpler than letting the model rephrase the server's wording, and nothing to validate. |
| D4 | Dependency rule implemented as an implied "reported to the bank: yes" candidate for every bank reply (acknowledged, interim or final), from the same source. A "No" elsewhere then becomes an ordinary conflict. If resolutions still combine "No" with a kept reply, freezing the facts is refused (`inconsistent_facts`). "A final reply needs a written complaint or report" is satisfied by the same implied report. | Reuses the existing conflict screen instead of a new kind of finding. |
| D5 | New output checks: a bank reply kept without a document must be attributed (and the "You told us that" fallback covers it); "the bank replied" with confirmed "not told" is a contradiction; text saying both fails; "the user"/"the claimant" fails in the free evaluation. | Elena's three validator items. |
| D6 | Journey questions are a dashboard step before the intake form (`S1-Journey`), shown until the first journey answer is saved. Answers are `journey_*` case responses. The final-reply letter is uploaded in the existing evidence step, not on the journey screen. | Elena's order (story, journey, intake). Re-uses the responses route and evidence upload; no new upload control. |
| D7 | The confirm screen runs inside the dashboard (`S1-Tier0DraftPending` renders it, headed "Next: confirm your facts"). Confirming generates the free evaluation straight away; there is no separate "Get my free evaluation" click inside the dashboard. The standalone `/facts` page stays. | One fewer click. The snapshot is fresh at that moment, so nothing is lost. |
| D8 | While paid stages are off, every state after the free evaluation (`S1-Tier0Draft`, `T-BuyReportCTA`, `T-EligibilityGate`) shows the evaluation plus "Your next steps": the recommendation from the confirmed facts and the two paid cards with "Available from [date]". | Avoids rewiring the paid states, which return unchanged when stage 2 switches on. |
| D9 | "Email me when it's available" stores the address on the signed-in account (from `profiles`), never a typed one, in `public.waitlist` with source `stage2:bank_pack` / `stage2:fidrec_pack`. The table allows one row per email, so a second product is added to the row's source list. Rate limited. | Simplest, and no new personal data is typed in. |
| D10 | Tests that need a real checkout (`checkout-provider` contract, both `checkout-failures` tests, the fresh-account purchase) are skipped while `HARBOR_PAID_STAGES_ENABLED` is not `true`, with the reason "Stage 2: paid stages are off". New stage 1 tests run instead: checkout refuses both products with `product_not_available`, and a fresh account completes the free path through to the next steps. Nothing is deleted; with paid stages on, the original tests run unchanged. | Elena: CI green except what is deferred to stage 2, listed explicitly. |
| D11 | The recommendation API answers 200 with no recommendation for cases that have no confirmed free snapshot (cases evaluated before fact checking). | A 409 would be logged as a browser error on those cases, and there is nothing wrong to report. |
| D12 | 768-px fix: the dashboard sets `data-harbor-ready="true"` once the queries that decide its state have settled; the state tests wait for that instead of "network idle", which a polling page reaches only by chance. No timeout was lengthened. | Elena: wait for an app-level ready signal, don't lengthen timeouts. |
